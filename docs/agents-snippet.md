## Span lifecycle (MCP only)

When work touches unfamiliar code, cross-boundary effects, or saved meaning: use Span. Skip it for trivial local edits.

- When starting: use the operation the task needs — `explain` for explanation, `trace` for flow, `impact` for change risk, `authority` for governance, `status` for coverage/freshness. No status preflight is required; semantic operations already report uninitialized/unavailable. An automatic `HOOK_FAST` notice is event-local by design. If a normal `status` or semantic operation returns store readiness only where coverage is expected, that is unexpected: record it, do not infer semantic completeness, and continue with exact-target `explain`/`status` only when needed. `store_readiness: READY` means store works, not understood.
- Before any repository-scoped call, obtain the exact canonical registered `repository_id` from `tools/list` or a successful `initialize_repository` response. Never pass a filesystem path as the ID; preserve the registered value unchanged.
- When repo is `UNINITIALIZED`: stop normal work. `initialize_repository` runs once, in a dedicated setup session. No interpretation happens here.
- When user gives an exact directory: `initialize_target` with that exact scope plus objective; it returns the next typed unit, advance via `submit_interpretation`. Account for every inventory member bound in the returned mapping batch. Cover every material area with a persisted disposition; one answer is never completion; close with fresh `status`/`explain` readback. For each newly admitted area Span creates the first-admission CQ-01 seed itself; do not manufacture it. Otherwise use question-local `explain`; use `establish_baseline=True` only to baseline an ordinary root.
- When edit is material: `impact` with target plus change before editing. Pre-change brief (impacts, conditions, authority, verification, blockers), never approval.
- When path or governance is unclear: `trace` (producers, carriers, consumers, boundaries, lifecycle path) / `authority` (sources with status, applicability, precedence, conflicts side-by-side), only where required.
- When Span returns `PendingInterpretation`: do that one bounded slice with your model, follow its brief for that slice only, then `submit_interpretation`. Returns the answer or the next pending unit; repeat until an answer returns. A malformed payload or semantic rejection reuses the same continuation after correction; an expired or lost continuation is recovered by re-running the original idempotent operation. There is no separate reissue operation.
- Opaque values: pass a returned page token unchanged to the same operation with the same request arguments; pass a returned `continuation` unchanged to `submit_interpretation`. Never decode, edit, or synthesize either value.
- When editing: use outside tools. Span never edits, runs tests, orchestrates, selects or invokes models, or writes target. Ordinary Span reads and hooks never rebuild structural state; repository setup and explicit `refresh` may invoke the shell-owned structural provider's bounded currency operation. Agents never run or manage the provider build themselves.
- When done editing, same change, editing agent owns it: scoped `status`, then outside tests, then scoped `refresh` (explicit reinterpretation of stale scope, never automatic, never expands scope), then scoped `status` again. Bare `refresh` proves nothing.
- When you need structure, not meaning: `locate` (find a symbol, outline a file, list target members) / `neighbors` (bounded callers/callees, upstream/downstream/both). Both return navigation evidence only — cite it as evidence, never as authority. In-body content search stays with grep.
- Hooks only call `status` in `HOOK_FAST` (compact notice only). They never initialize, explain, impact, trace, authority-check, refresh, interpret, or rebuild.
- Keep `PARTIAL`/`AMBIGUOUS`/`CONFLICTED`/`UNRESOLVED`/`STALE`/`UNVERIFIABLE` verbatim. Missing authority stays missing.
