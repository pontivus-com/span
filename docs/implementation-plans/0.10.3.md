# Span 0.10.3 implementation plan — low-friction lifecycle

Date: 2026-11-14. Status: **implementation in progress; T03 complete; T07 next; product/host verification deferred**.
Source baseline: the user's accepted usability review and per-issue solution
baseline in the 2026-11-14 conversation. Repository inspection: `a12eec7`.

## 1. Authority, purpose, and scope

This document contains the solution design and its associated implementation
tasks for bugfix release 0.10.3. Sections 1–11 define the solution; §12 orders
the work and §13 records completion. It is not a new requirements layer.
The authority chain is [AGENTS.md](../../AGENTS.md), [requirements pyramid](../requirements-pyramid.md),
[goals](../goals.md), [foundations](../foundations.md), [lifecycle contract](../lifecycle-contract.md),
[functional design](../functional-design.md), then [technical design](../technical-design.md).
References below use their G, A, F, L, and FD identifiers rather than restating them.
Public-contract decisions are now recorded in their owning amended layers.
This plan does not override those layers or claim the installed code conforms.

This development branch began with the documentation correction: the relevant
behavior-class audit and amendments to lifecycle, functional, technical and plan
authority from the accepted baseline and code evidence. Runtime implementation is
now in progress under the task sequence below: T03 is complete and T07 is the next
implementation dependency. This state does not bump the package version, authorize acceptance runs, or
authorize publication. Remaining implementation follows the task boundaries and
gates below. File paths in task boundaries are relative to the Span root.

The design covers obtain, investigation evidence, retain, receipts, identity,
status, and repeated evidence delivery. It preserves the existing semantic writer,
typed support owner, status computation, store, and three lifecycle operations.
It introduces no model runtime, semantic similarity service, structural index,
automatic conclusion author, delivery ledger, or additional public tool.

## 3. Implementation derivation

Public inputs/results are owned exclusively by lifecycle §4.1–§4.3; deterministic

## 4. Obtain/evidence implementation boundary

Lifecycle §4.1 owns all obtain, selector, source-pointer, admission and page
fields. FD-25/28 and FD-54–57 own selection/classification and bounded delivery;
technical §9.2/§11 selects their mechanism. Implement through the existing answer
composer and evidence service. Evidence E1/E5 explains the selection change;
target behavior is not redefined here. T03 migrates shapes; T04 implements obtain
and evidence behavior after T07's state/failure repairs.

## 5. Recording/schema implementation boundary

Lifecycle §4.2 owns request alternatives, qualification fields and record
results; FD-3/30/39–41/59–60 owns acceptance, scope and failure behavior.
Technical §9.2/§12 chooses canonical constraint generation and service/store
composition. T03 implements declarations and their mechanical consumer migration;
T05 handles stateful recording against them. E2 justifies the schema-equivalence
regressions. No task chooses an alternative public field set.

## 6. Context implementation boundary

Lifecycle §4.1/§4.3 owns public context references and re-establishment guarantees.
FD-2/45 owns issuance/recovery behavior; technical §9.2 selects the shared
contexts.issue_context mechanism. E8/E9 supplies code-proven defects and regression
cases. T03 migrates the public reference and typed namespace access; T07 then
repairs stateful lookup, issuance and failure production. The observed original
failure remains in scope without requiring an unavailable transcript.

## 7. Compact result implementation boundary

The sole public field/type definitions are lifecycle §4.1–§4.2, including shared
admission delivery, compact qualification and exact receipt/run detail retrieval.
Technical §9.2 identifies canonical projection/store owners. T03 implements those
shapes and their direct call sites; T06 composes evaluator/status outputs into
them. E7 identifies the existing audit owners. Do not copy a public-field table
into this plan or delegate a missing payload decision to an implementation task.

## 8. Status/delivery implementation boundary

Lifecycle L1/L9 and FD-59/60 govern scope/status; use the existing
compose_surface_status owner. T06 owns its result composition and T08 the active
projections of the changed grammar. E5 distinguishes response volume from
whole-task value; T09 measures the latter. No new status/index/delivery service
is part of this plan.

and decoding. Unexpected defects retain internal diagnostics but cross the MCP
boundary only as stable generic transport failure, never as raw exception text.

T03 owns discriminator/schema projection and public carrier mechanics. T07 owns
