## 0. Release identity

0.10.5 is **one patch release**. It contains both changes, in this order:

1. **Evidence reference remediation** — remove stored source excerpts; retain
   the calculated hash, reference, ranges and metadata; schema 12; delivery
   re-reads and verifies.
2. **Repository-portable backup** — write one artifact inside the related
   repository at `.span/backups/`, commit it with the code, and load it on a
   fresh deployment with explicit rebinding.

The backup change depends on the evidence change: committing a database that is
~70% duplicated source text would defeat the purpose of the artifact.

## 2. Problem A — evidence storage

### 2.1 Measured

| Measurement | Value |
| --- | ---: |
| External integration stores | excerpt payloads were roughly 70% of stored bytes |
| Real oversized evidence case | exceeded the configured evidence bound |
| Default `max_evidence_bytes` | 96,000 |

A whole-file `ask` admission or `record` create/update fails with
`evidence exceeds max_evidence_bytes`; the public result hides the cause. Ranged
support succeeds.

### 2.2 Non-compliance

- second copy of the repository instead of a reference;
- second representation of the same evidence;
- unbounded excerpts with no TTL/reaper/terminal;
- delivery bound applied to binding;
- contracts currently require the excerpt (`ports.md:28`,
  `lifecycle-contract.md:146-151`, `authority-trust.md:11`, `glossary.md:77`).

### 2.3 Target model

```text
SourceObservation
    observation_id
    repository_id
    evidence            # locator + full-file fingerprint
    content_digest      # sha256 of the delivered content (whole file or exact ranges)
    captured_at
    total_lines
    delivered_ranges
    whole_file
    # no excerpt
```

- **Admission:** read and hash; validate ranges and line counts; store the
  reference, hash and metadata. No delivery bound at binding. A 134 KB file is
  admitted whole.
- **Delivery:** re-read the current source; verify `content_digest`; slice the
  ranges; page large content at line boundaries. A mismatch is a typed stale
  outcome; new bytes are never presented as admitted.
- **Support:** unchanged; it already re-reads and compares hashes.
- **Continuation:** bound to the observation/digest; invalidated when the
  digest changes; never mutates the observation.

### 2.4 Schema 12

- Drop `source_observations.excerpt`.
- `SCHEMA_VERSION = 12`; `TARGET_SCHEMA = 12`;
  `SUPPORTED_SOURCE_SCHEMAS = {7, 8, 9, 10, 11}`.
- Add `store_transition_schema11.py` for the 11 → 12 table copy, excluding the
  dropped column; preserve counts, identities and hashes.
- The runtime never migrates at open. The transition is offline, verified,
  reversible.

## 3. Problem B — repository-portable backup

Each repository must carry its own deployable artifact:

```text
<REPO_ROOT>/.span/backups/<UTC timestamp>/
  <repository-id>.db
  manifest.json
  manifest.sha256
```

- Only that repository's store; no `install.json`, no `structural/`, no
  `transitions/`.
- Manifest format `span-repository-backup/1`: repository id, source root,
  created at, running code version, artifact path/hash/size, schema version,
  integrity, highest conclusion revision.
- Committed with the code; Span writes, the operator commits; Span never runs
  Git.
- Load requires the target basename to equal the repository id, verifies the
  artifact, snapshots the current data directory, replaces the store, and
  explicitly rebinds `repositories.root` from the source root to the target
  root.
- Reaping requires an explicit `KEEP`; Git history is the durable retention.

Commands:

```bash
span-install --backup-repository <REPO_ROOT>
span-install --verify-repository-backup <ARTIFACT_DIR>
span-install --load-repository-backup <TARGET_ROOT> [--repository-artifact <DIR>]
span-install --reap-repository-backups <REPO_ROOT> <KEEP>
```

The 0.10.4 full data-directory backup/restore remains for global recovery and is
not committed.

## 7. Acceptance criteria

1. No `source_observations` row stores source bytes; the column is removed in
   schema 12.
2. A 134 KB file is admitted whole without a delivery-bound failure.
3. Support evaluation returns `CURRENT` for unchanged content and
   `REASSESSMENT_REQUIRED` for changed content.
4. Delivery of unchanged content succeeds; changed content returns a typed
   stale outcome and never presents new bytes as admitted.
5. Large whole-file delivery pages at line boundaries.
6. A continuation becomes invalid when the digest changes.
7. 11 → 12 transition, verify and rollback pass on a disposable copy.
8. Database size drops by the measured excerpt share after the transition.
9. A repository artifact is written to `.span/backups/`, verified, loaded into
   a clone with a different absolute path and the same basename, rebound, and
   served through `ask` with `CURRENT` support.
10. A renamed clone, wrong root, legacy schema, held store, tampered artifact
    and missing `KEEP` all fail closed with actionable messages.
11. The full suite, Ruff, Black, typing ratchet and wheel build pass.
12. 0.10.5 is published with one changelog section covering both changes.

## 8. Risks

| Risk | Mitigation |
| --- | --- |
| Historical bytes no longer replayable | Contract states it; Git history is the archive; digest + ranges identify the state |
| Delivery re-reads the source | Hashing is cheap; delivery is paged; support already re-reads |
| Schema transition risk | Disposable-copy proof; backup; rollback; live transition separately confirmed |
| Two changes in one release | Strict phase order and separate gates; evidence first, backup second |
| Backup artifact size | Schema 12 removes the excerpt duplication first |
| Renamed clone cannot load | Fail closed with an actionable message; renaming out of scope |
