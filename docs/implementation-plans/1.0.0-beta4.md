## 1. Problem and release outcome

Beta 3 classifies `P2S` and `P2W` as the same governing-edge rank. The core
graph validator rejects a declared `P2W -> P2S` governing edge because the
current rank comparison requires every governing parent to have a strictly
lower rank than its child.

That makes an otherwise well-formed Functional Pyramid candidate fail with
`INVALID_GOVERNING_EDGE` even when the relationship is explicit. The defect is
in Span's contract-layer derivation model, not in declaration syntax,
repository membership, authority ownership or the public MCP grammar.

FD-67 is the sole product owner of the corrected contract-sublayer
derivation behavior. This plan does not create or copy that normative rule.
FD-72 separately owns deterministic route presentation, and Technical Design
§18 derives one semantic edge-admissibility mechanism from FD-67 while keeping
it independent from presentation ordering.

The Beta-4 outcome is complete only when candidate validation, ACTIVE health,
ordinary route resolution and reverse authority navigation agree on the same
declared graph relation through the installed product.

## 2. Non-goals and hard boundaries

Beta 4 does **not**:

- infer a P2 governing relationship because two rules or contexts are jointly
  applicable;
- infer governance from repository topology, file names, document class,
  prominence, similarity, enum position or source order;
- use route/presentation rank as the semantic owner of edge admissibility;
- add another declaration grammar, graph carrier, DTO, semantic writer,
  persisted reverse index or impact registry;
- change the `FunctionalPyramidLayer` public vocabulary;
- change repository schema 15, installation Functional Pyramid schema 1,
  Functional Pyramid declaration version 1, `FunctionalGraphRef`, public MCP
  request/result shapes or the three-tool `ask`/`record`/`reconsider`
  surface;
- add a repository- or adopter-specific exception to the generic resolver;
- make private external integration declarations, identities, receipts or raw
  acceptance material public Span repository content;
- weaken, delete or bypass an existing correctness, architecture, typing,
  formatting, coverage, packaging, release or DCO gate; or
- treat implementation completion, merge, CI success or a release-ready verdict
  as publication authorization.

## 3. T00 · Requirements and solution-design closure

**Authority:** requirements-pyramid §§2–7; G7–G8; F1, F5, F11, F12, F14;
L12–L16; FD-66–FD-73.

The authority chain is closed before runtime work begins:

   relationships, separates composition from judgment, and keeps participation
   from implying applicability (F5/F11/F12).
3. Layer 2 already requires declared routes, pure candidate validation,
   participation/health separation and one cross-repository governance lifecycle
   (L12–L16). No Layer-2 contract change is required.
4. FD-67 now specifies the missing deterministic contract-sublayer derivation
   rule.
5. FD-72 owns deterministic presentation independently from admissibility.
6. FA-02/FA-15/FA-21 define the required candidate, graph-defect and reverse
   navigation demonstrations.
7. Technical Design §18 selects one pure governing-edge admissibility owner in
   the core and prohibits rank/enum/presentation-derived validity.

No T01+ task may compensate for a missing requirement locally. If implementation
reveals another product rule is needed, reopen the owning layer first.

## 4. Implementation and verification sequence

### T01 · Reproduce the published Beta-3 defect

**Status: OPEN.**

**Baseline:** exact published Beta-3 commit
`6bbc84f7e074cf8532ed773b0f3fde736a03f0d7`.

Construct a generic Functional Pyramid fixture with a declared P2W rule whose
direct governing-rule IDs include a P2S rule. Do not use private adopter
declarations or identifiers.

Prove on the immutable Beta-3 baseline that:

1. both declarations decode successfully;
2. repository/member/declaration validation has no unrelated blocker;
3. structural graph evaluation reports `INVALID_GOVERNING_EDGE` for the
   explicit P2W-to-P2S relationship; and
4. the candidate is not activation-ready because of that graph finding.

**Exit:** retained test/log evidence demonstrates the released defect before the
runtime semantic correction is applied. No production code is changed merely to
obtain the reproduction.

### T02 · Introduce the singular governing-edge admissibility owner

**Status: OPEN.**

**Authority:** FD-67; Technical Design Part C §18.

In `src/span/core/functional_pyramid.py`, introduce one pure closed
governing-edge admissibility relation for non-ROOT rule edges. The exact private
helper name may follow local conventions, but there is one semantic owner.

Required integration:

- `_rule_edge_findings` delegates edge classification to the canonical
  relation;
- `_resolve_rule_refs` delegates the same classification to that relation;
- candidate validation and ACTIVE health continue to receive structural
  findings through the existing graph-health path;
- ordinary route traversal uses the same relation rather than an independent
  comparison; and
- P0/`ROOT` remains on its existing dedicated terminal rule.

The existing route-order rank helper may remain or be renamed, but it implements
FD-72 presentation only. It must not be called to determine whether a governing
edge is legal. Enum declaration order is likewise not semantic authority.

**Exit:** source inspection shows one edge-admissibility owner and no duplicated
rank-based semantic check.

### T03 · Add discriminating core and service regressions

**Status: OPEN.**

**Authority:** FA-02, FA-15, FA-21; Technical Design §18.

Add the minimum discriminating generic fixtures/tests required to prove:

1. explicit FD-67 permitted contract-sublayer derivation resolves;
2. its reverse is `INVALID_GOVERNING_EDGE`;
3. a P2S-to-P2S governing edge is invalid;
4. a P2W-to-P2W governing edge is invalid;
5. joint applicability without a declared edge creates no relationship;
6. valid candidate evaluation is `activation_ready=true` when no other
   blocker exists;
7. the same invalid edge set degrades ACTIVE structural health;
8. ordinary forward route resolution reaches the declared governing parent;
9. exact canonical-owner reverse navigation exposes the declared dependent; and
10. route output order follows FD-72 without using that order as proof of edge
    validity.

Correct any draft assertion that reads a non-existent view field; unresolved
route state is read through the canonical `FunctionalPyramidView` carrier.

**Exit:** the focused core/service regression lane is green and fails when the
canonical edge relation is deliberately regressed.
