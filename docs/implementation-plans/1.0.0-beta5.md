# Span 1.0.0 Beta 5 implementation plan

This programme records implementation, verification and release decisions.
[Span’s requirements pyramid](../requirements-pyramid.md) and its governing
layers own product behavior.

The campaign starts from published Beta 4 commit
`f513f753ca164a844851c4cdf720a6257d81f0f6` on `release/1.0.0-beta5`.
The target package version is `1.0.0b5`, with Git tag `v1.0.0b5` and
MCP Registry version `1.0.0-beta.5`.

## Cold participation write

An activation dispatched to a fresh process can fail with a storage
unavailability result. The installation transaction reserves writes on the
member databases. Candidate revalidation then opens a member's lifecycle store
on another connection, which also needs a write reservation. A validation
request in a different process cannot prepare the connections in the process
that accepts the write.

The fix belongs in the shell transaction preparation mechanism under
[Technical Design](../technical-design.md). Goals G3 and G8, foundations F7 and
F12, lifecycle contract L14 and functional design FD-85 and FD-93 govern the
change. Open existing raw member runtimes without acquiring a separate write
reservation. Keep operational expiry cleanup at the ordinary service-context
boundary. Keep final FD-84 candidate validation,
participation and dependent effects, accepted contexts, and the receipt in the
same atomic write. Preserve receipt replay and conflict semantics. This change
uses schema 15, installation schema 1 and the existing public MCP operations.

The full suite also exposed a provisioning fixture that still called an old
entrypoint and expected schema 12. The fixture now exercises the existing
provisioning owner and checks the persisted canonical root and current schema.

## Directory document chains

G7, G8, F11 and F12 establish the correction for Beta 5. A directory query
must return the canonical documents relevant to that directory, from P0
through the deepest applicable layer. The resolver in Beta 4 follows declared
rule IDs and projects their owner bindings. Grouping those bindings by owner
would still omit relevant documents that have no rule declaration.

Carry the amended requirements through L12 and L14, the FD-62–FD-75 routing
and support behavior, and the technical design. Replace the rule-level
declaration and projection with a document-based route through the existing
`ask` operation. Carry the route change through candidate validation, retained
normative support, dependency indexing and reconsideration. Document the
operator transition for existing declarations and retained support before
enabling that transition on an installation. Preserve existing retained
conclusions and historical receipts. Reassess conclusions whose governing
basis changed.

Installed acceptance must query root, nested and sibling directories across
generic repositories, including directories without a registered semantic
surface. It must show inherited documents, relevant directory-specific
documents including guidance with no rule IDs, shared ancestors and the
deepest applicable design. It must keep sibling-only material out of the
selected route, allow applicable branches to skip layers where no document
applies, and expose genuinely unresolved references. Verify both successful
multi-repository resolution and the effect of a changed governing document
or relationship on retained support. Record the implementation and evidence
before release. Installed verification is pending.

### Required implementation sequence

The correction is one coordinated contract migration. The tasks below are
ordered. A later task cannot be accepted while its governing design or carrier
task remains incomplete.

   F11/F12, lifecycle L12/L14, functional design FD-62–FD-94 and technical
   design §§17–22 so they describe whole canonical documents, explicit directory
   scopes, total directory resolution and document relationships consistently.
   Remove Functional Pyramid rule IDs, rule anchors, rule-owner routes and
   section-level placements from every governing layer. Preserve ordinary uses
   of the word “rule” outside the Functional Pyramid domain.

   *Status: closed 2026-11-25.* The requirements correction is complete. Closing
   it removed the last retired-vocabulary residues, gave `INVALID_PLACEMENT_SCOPE`

   invariant, glossary and freshness statements. Implementation tasks 2–11 remain

   `FunctionalPyramidDirectorySelector`. Make

### Design acceptance checkpoint

Implementation may proceed only when the requirements, lifecycle, functional
and technical designs agree on all of the following:

- the Functional Pyramid node is a whole canonical document placement with an
  explicit repository-relative directory scope;
- placement scope selects the relevant branches for an exact directory, and
  ancestor scopes compose additively;
- the returned branch can span P0, P1, P2S, P2W, P3 and P4, skipping only
  layers for which no applicable document is declared;
- no Functional Pyramid API, declaration, finding, provenance or support
  carrier contains a rule ID or rule anchor;
- initialization, candidate validation, ACTIVE health, retrieval, normative
  support, reconsideration and cutover all use the same placement graph;
- participation is whole-repository, and a mandatory root-scoped P0 placement
  makes every directory return a pyramid; and
- no query returns `UNCOVERED_PATH`, `OUTSIDE_FUNCTIONAL_SCOPE` or an empty
  governing projection.

## Verification and release gates

1. Reproduce cold activation on the published baseline using two generic
   repositories. Validate the candidate in one MCP process and send activation
   as the first tool call of a fresh process.
2. Verify the fix through the non-editable installed-MCP journey. Require
   receipt acceptance, ACTIVE and VALID member status, resolved governance,
   dependent effects and receipt replay. Preserve the existing atomicity and
   concurrency checks. Record measured test budget growth in its baseline.
3. Complete Ruff, Black, the zero-error typing ratchet, the complete Python and
   plugin suites, and distribution verification. Record evidence in the
   [acceptance record](../acceptance.md). Keep raw verification material private.
4. Obtain independent review, reconcile the reviewed candidate to `master`,
   and require the normal CI checks on that exact master commit.
5. Obtain release-owner authorization for the exact reviewed master commit and
   `1.0.0b5`. Follow the [release procedure](../contributing.md#releases) and
   verify published artifacts against that identity.

Record additional observed defects with their reproduction, governing authority and
verification before including their corrections in this campaign.

## Preview follow-up

When the installer uses a custom binary directory and another Span binary
appears earlier on the executable search path, host registration can select
the earlier binary even after the installer verifies the new distribution.
Investigate the registration executable selection against the owned install
identity. Add an isolated regression that installs a preview alongside an
existing binary and checks the executable recorded for each selected host.
