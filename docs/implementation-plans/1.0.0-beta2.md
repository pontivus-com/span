## 1. Defect statement

### B2-D01 — `span-install` does not execute the repository initialization contract

The public initialization contract requires the installer to:

1. bind each selected repository's canonical root;
2. register caller-declared authority seeds and authority bindings;
3. create/open the schema-14 repository lifecycle store; and
4. create/verify the installation Functional Pyramid store.

Beta 1 contains the canonical implementation of that behavior:

- `src/span/core/model/administration.py::InitializeRepositoryRequest`;
- `src/span/service/administration.py::initialize_repository`;
- `src/span/shell/context.py::provision_repository_runtime`.

However the released `src/span/shell/install/cli.py::_provision_runtime` never
calls that path. It parses `--authority-seeds-file`, provisions the Python
runtime/indexer and writes host configuration, but does not dispatch an
`InitializeRepositoryRequest`. Its receipt explicitly records
`seeds_resolved_and_active: false`.

The released installer also has no administrative input for the already-existing
canonical `AuthorityBinding` carrier. Functional Pyramid rule declarations
carry `owner.authority_ref`, and
`FunctionalPyramidService._authority_bindings` requires that reference to
resolve through the repository's existing authority bindings. A clean installer
path therefore cannot establish the authority state required by a real
Functional Pyramid candidate.

**Observed consequence:** a repository can have Span installed/registered and
still have `authority_bindings_json=[]`. Functional Pyramid candidate
validation then reports that the functional rule owner is not a declared
authority binding. This is not an adopter-rule defect; the setup path never
registered the declared generic authority state.

### B2-D02 — Beta-1 production-topology acceptance bypasses B2-D01

The installed cross-repository journey in
`tests/integration/test_installed_mcp.py::_create_governed_stores` constructs
`LifecycleStore` instances directly, calls `register_repository` directly,
and injects `AuthorityBinding` values directly before starting the installed
MCP server.

That fixture correctly proves post-setup Functional Pyramid runtime behavior,
but it bypasses `span-install`. Therefore Beta-1 T10/T11 could pass even while
the production installer violated its initialization contract.

This is a verification defect at the production-topology boundary, not a reason
to weaken or discard the existing Functional Pyramid tests.

## 2. Root cause

The defect is a Layer-4 composition omission.

Beta 1 had all required canonical owners independently:

- the explicit-only initialization contract;
- the canonical administrative request/result;
- the repository initializer;
- the raw repository provisioning composition root;
- the repository lifecycle authority storage;
- the Functional Pyramid authority resolver;
- the installer;
- the installed cross-repository runtime acceptance lane.

The installer was never wired to the existing provisioning owner, and the
installed acceptance fixture independently manufactured the post-setup state.
The two omissions masked each other.

No Layer-0–3 product rule is missing. No schema or persisted state model is
missing. No new MCP operation is required.

## 3. Correct solution design

The governing mechanism is fixed in technical design §20.

### 3.1 Canonical owner reuse

Beta 2 must reuse exactly:

- `InitializeRepositoryRequest`;
- `InitializeRepositoryResult`;
- `EvidenceRef`;
- `AuthorityBinding`;
- `initialize_repository`;
- `provision_repository_runtime`;
- the repository `LifecycleStore`;
- the installation Functional Pyramid store.

Do not introduce a setup DTO, authority manifest domain type, second authority
registry, compatibility decoder, implicit authority discovery, or another
repository writer.

### 3.2 Explicit repository-qualified administrative ingress

The installer grammar is:

```text
--repo REPO_PATH                                  repeatable
--authority-seeds-file REPOSITORY_ID PATH        repeatable
--authority-bindings-file REPOSITORY_ID PATH     repeatable
```

Each configuration file is a strict JSON **list of the existing canonical
carrier**, not a new wrapper:

- seeds file → `EvidenceRef[]`;
- bindings file → `AuthorityBinding[]`.

The repository-id argument is shell routing metadata only. Every decoded item
must carry the same repository id.

This intentionally replaces the Beta-1 one-argument
`--authority-seeds-file PATH` grammar. That grammar never completed the
promised initialization and is not retained through an alias or compatibility
parser.

### 3.3 Preserve canonical tri-state setup semantics

For each selected repository and each configuration family:

- no mapped file → `None` → preserve existing declarations;
- mapped file containing `[]` → `()` → clear;
- mapped non-empty file → replace with the exact decoded tuple.

This is the existing `initialize_repository` contract and must not be
reinterpreted in the shell.

Reject before mutation:

- duplicate `--repo` identities;
- duplicate seed/binding mapping for one repository;
- mapping for a repository not selected with `--repo`;
- malformed JSON;
- wrong canonical type;
- item repository id different from the mapping repository id.

Authority kind, status, applicability, precedence, locator, fingerprint and
repository ownership are never inferred.

### 3.4 Installer composition and order

The mutating installation path is:

```text
parse args
→ resolve selected repository ids
→ decode/validate every supplied authority file
→ collect read-only preflight facts
→ prepare/install Span runtime and structural indexer
→ take the existing data-directory backup before repository-state mutation
→ for each selected repository:
     construct one InitializeRepositoryRequest
     call provision_repository_runtime
     retain InitializeRepositoryResult
     close raw repository runtime
→ register hosts
→ observational verify_installation
→ write receipt from observed initialization results
```

`provision_repository_runtime` remains responsible for:

- structural `ensure_current`;
- Functional Pyramid installation-store creation/verification;
- repository-store open/create;
- filesystem evidence access;
- exact locator validation;
- `initialize_repository` dispatch.

The installer must not duplicate any of those mechanics.

`--dry-run` and `--verify-only` perform no repository initialization.

Repository initialization is not Functional Pyramid participation. Successful
setup leaves a registered repository UNCONFIGURED unless an ordinary
`record(kind="functional_pyramid")` lifecycle write activates or excludes it.

### 3.5 Failure and receipt semantics

Initialization is repository-local administration. Beta 2 does not invent a
cross-repository setup transaction.

All deterministic configuration errors must be rejected before mutation.
If a later operational failure occurs after a previous selected repository was
successfully initialized, the installer stops, names the failed repository and
retains the existing pre-mutation backup. It does not silently continue and it
does not fabricate all-or-nothing state.

The install receipt records the actual `InitializeRepositoryResult` for every
repository successfully initialized, including:

- repository id;
- canonical root;
- repository schema version;
- structural status;
- store readiness;
- resulting seed count;
- resulting binding count.

Input presence is not success evidence.

## 4. Implementation sequence

### B2-T00 — defect intake and design closure

**Status:** COMPLETE when this plan and the technical-design amendment are
reviewed and accepted.

Required evidence:

- Beta-1 installer source showing no
  `provision_repository_runtime`/`initialize_repository` call;
- initialization contract §§1–2;
- canonical initializer tri-state semantics;
- Functional Pyramid authority-owner resolution requirement;
- installed-MCP fixture direct store/binding setup.

No production code change before T00 is accepted.

### B2-T01 — failing regression baselines

Create behavior-level failing tests against unmodified Beta-1 behavior.

Required baselines:

1. clean single-repository `span-install` with a seed file does not establish
   the declared seed in the repository store;
2. clean repository initialization cannot supply the canonical authority binding
   required by a Functional Pyramid rule owner;
3. production-topology installed test setup is shown to bypass `span-install`;
4. `--verify-only` remains observational.

Do not modify assertions to fit the implementation.

### B2-T02 — close administrative ingress

Implement the repository-qualified repeatable seed/binding arguments and strict
canonical decoding.

Requirements:

- no new domain carrier;
- decoder uses the canonical model decoder;
- all files decoded before mutation;
- exact repository-id matching;
- duplicate/unselected mappings rejected;
- omit/clear/replace semantics represented exactly;
- no compatibility alias for the broken Beta-1 seed flag.

Add unit coverage for all grammar and tri-state cases.

### B2-T03 — wire installer to canonical repository provisioning

After runtime/indexer preparation and backup, construct one
`InitializeRepositoryRequest` per selected repository and invoke
`provision_repository_runtime`.

Requirements:

- exactly one canonical provisioning path;
- close every returned raw runtime;
- no partial `ServiceContext` construction;
- no runtime implicit initialization;
- no Functional Pyramid participation write;
- host registration occurs only after repository setup;
- `--dry-run` and `--verify-only` remain non-writing.

The receipt must project actual initialization results.

### B2-T04 — close the acceptance escape hatch

Change the production-topology installed-MCP acceptance lane so its participating
repository stores and authority bindings are established through the installed
`span-install` command.

The lane must then execute the unchanged Functional Pyramid lifecycle:

```text
clean target repositories + empty data dir
→ installed span-install initializes both repositories
→ installed span-mcp reports both repositories registered/UNCONFIGURED
→ FunctionalPyramidCandidateSelector validates the cross-repository candidate
→ record(kind="functional_pyramid", action="activate")
→ exact status is ACTIVE + VALID
→ ordinary ask returns cross-repository governing projection
→ NORMATIVE record derives route + canonical external authority support
→ authority support qualifies CURRENT
```

The acceptance fixture must not call
`LifecycleStore.register_repository` or write authority configuration directly
for this lane.

Lower-level unit tests may continue to construct stores directly where store or
service behavior itself is the subject under test.

### B2-T05 — generic verification

Run and pass:

- targeted installer/initialization tests;
- initialization-contract tests;
- administrative-readiness tests;
- Functional Pyramid service/resolution tests;
- installed non-editable MCP production-topology journey;
- complete FA-01–FA-44 functional acceptance map;
- full pytest suite;
- Ruff;
- Black;
- zero-error typing ratchet;
- package build/non-editable install;
- exactly three MCP operations;
- backup/recovery checks affected by installer mutation ordering.

No test, assertion, budget or architecture guard may be weakened to pass.

### B2-T06 — first-adopter revalidation

Because Beta 2 changes runtime/setup implementation, Beta-1 T13 requires the
private first-adopter acceptance to be rerun.

Use the adopter repositories' own committed declaration/configuration and
private acceptance material. Classify failures exactly as Beta 1 T11 requires:

- generic Span defect → fix Span at owning layer;
- adopter declaration/configuration defect → fix adopter repository;
- unresolved adopter authority → leave unresolved;
- adopter-only preference → do not add to Span.

Only sanitized generic evidence may be committed to Span.

Beta-2 acceptance requires a cold install from repository-controlled inputs,
candidate validation, activation, ACTIVE+VALID status and at least one real
governing projection on the adopter surface that exposed B2-D01.

### B2-T07 — release assembly

Advance only release identity, not schema identity:

- `src/span/__init__.py` → `1.0.0b2`;
- tag → `v1.0.0b2`;
- GitHub prerelease title → `Span 1.0.0 Beta 2`;
- MCP Registry server → `1.0.0-beta.2`;
- MCP Registry PyPI package → `1.0.0b2`.

Repository schema remains 14 and Functional Pyramid installation schema remains
1 because this remediation changes no persisted contract. This is explicitly
permitted by technical design §21.

Update:

- changelog with B2-D01/B2-D02 and verified correction;
- install documentation with the exact repository-qualified authority-file
  grammar;
- acceptance documentation with sanitized Beta-2 evidence;
- release/version tests and generated registry projection.

## 5. Non-goals

Beta 2 does not:

- add a fourth MCP tool;
- alter Functional Pyramid candidate or record grammar;
- change repository schema 14;
- change installation schema 1;
- add authority inference;
- derive authority bindings from Functional Pyramid declarations;
- copy canonical rule prose into Span;
- auto-activate participation during install;
- add adopter-specific repository IDs, rule IDs, paths or topology to Span;
- create a repository-side setup DTO;
- add compatibility parsing for the broken Beta-1 seed CLI;
- treat adopter source-control omissions as a Span product defect.

## 6. Acceptance gates

Beta 2 is not complete until all are true:

1. a clean installed `span-install` can create/bind a repository and establish
   exact declared seeds/bindings through the canonical initializer;
2. omit/clear/replace semantics are proven at the installer boundary;
3. a clean two-repository installed lane reaches Functional Pyramid
   ACTIVE+VALID without direct store setup;
4. the same lane proves cross-repository canonical authority support qualifies
   CURRENT;
5. `--verify-only` and runtime MCP remain non-initializing;
6. exactly three MCP tools remain;
7. no schema migration is introduced;
8. full generic verification is green;
9. the private first-adopter rerun passes or returns an explicitly classified
   blocker;
10. release metadata deterministically resolves to Beta 2.
