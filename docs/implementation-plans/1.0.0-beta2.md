## 1. Outcome

Deliver the Beta-2 maintained-knowledge lifecycle in which:

1. the working engineering agent records supported semantic meaning while the
   evidence and reasoning are fresh;
2. that exact semantic revision is retained as `CAPTURED`, not automatically
   published as shared knowledge;
3. a separate reviewer/curator act accepts a stable exact revision as
   `CURATED`;
4. ordinary `ask` Answer content is available only while the revision is both
   `CURATED` and its required support is `CURRENT`;
5. implementation/governance change continues through the same
   `reconsider`/re-establishment lifecycle;
6. semantic-preserving `confirm` may inherit an existing curation decision,
   while semantic change returns the new revision to `CAPTURED`; and
7. Functional Pyramid authority remains independent from curation.

The public MCP operations remain exactly:

```text
ask
record
reconsider
```

Curation is an understanding update inside `record`; pending curation is
obtained through `ask`.

## 2. Non-goals and hard boundaries

Beta 2 does **not**:

- add a fourth `curate` MCP operation;
- run a model or background curator inside Span;
- require LangChain, LangSmith or another external framework;
- make curation proof of semantic truth;
- make curation a Functional Pyramid authority layer;
- infer authority, applicability or semantic quality from repository structure;
- add another semantic content store, writer, support evaluator or effect engine;
- add DTO/shadow carrier families or compatibility grammar;
- similarity-rank or model-rank pending curation;
- weaken support/currentness requirements;
- auto-curate Beta-1 conclusions during migration;
- silently dual-open schema 14 and schema 15;
- make external articles/social communication product authority.

External knowledge-factory material was discovery evidence that prompted the
design review. The repository's canonical layers now own the resulting Span
requirements independently.

### T05 · Implement curation through the existing understanding writer

**Authority:** L4, L17; FD-96–FD-98, FD-102; Technical Design §24.2.

Extend the existing understanding update owner; do not create a curation service
with separate semantic transaction ownership.

For an explicit curation update:

1. receipt/replay resolution remains first;
2. compare `expected_version`;
3. resolve every target lineage to its exact current revision;
4. evaluate existing required support;
5. reject the whole update through the existing typed validation path if any
   target is non-current;
6. create one unchanged-membership understanding version;
7. write one EXPLICIT curation disposition per target;
8. commit the ordinary receipt atomically;
9. return ordinary `UnderstandingRecorded`, with the curated refs in
   `affected_revisions`.

A curation action cannot share one update with
add/confirm/correct/replace/withdraw.

Transition behavior:
- create/add/correct/replace → CAPTURED;
- withdraw → non-reusable;
- confirm of CURATED semantically unchanged predecessor → new revision plus
  INHERITED_CONFIRMATION disposition pointing to the predecessor;
- confirm of CAPTURED predecessor → CAPTURED.

If review finds semantic defects, use the existing challenge/correct/replace/
withdraw lifecycle before curation.

**Exit:** service/store/MCP tests prove CAS, atomicity, replay/conflict, mixed
target rejection, no semantic revision on curate, and exact inheritance.

## 6. Cross-cutting compliance gates

### C1 — Requirements-pyramid derivation

Every changed behavior maps upward to the canonical G/A/F/L/FD owner. A rule
that exists only in Layer 4, this plan or code blocks completion.

### C2 — Functional Pyramid independence

Curation cannot create or mutate participation, health, applicability, route
identity or authority support. Normative reuse still requires both CURRENT
governing/empirical support and CURATED semantic reuse state.

### C3 — One semantic implementation path

No second semantic writer, curation DTO family, answer composer, support
evaluator, dependency-effect engine or shell semantic coordinator.

### C4 — Three-tool boundary

Advertised MCP operations remain exactly `ask`, `record`, `reconsider`.
Curation grammar is inside those operations.

### C5 — No invented review

Migration, support evaluation, governance resolution and unrelated writes may
not manufacture EXPLICIT curation. INHERITED_CONFIRMATION exists only for the
Layer-3-approved semantic-preserving confirm transition from a CURATED exact
predecessor.

### C6 — Historical truth

Historical snapshots must show that a semantic revision existed as CAPTURED
before later explicit curation. No read path retroactively projects a future
curation into an earlier understanding version.

### C7 — Currentness and curation are orthogonal

Curation acceptance itself requires CURRENT support. Later support loss does not
erase curation history, but it removes the revision from Answer until
re-established. CAPTURED non-current revisions are stale, not pending.

### C8 — Explicit migration

A schema-14 store never opens as schema 15 by fallback or implicit mutation.
Transition and rollback remain explicit and separately observable.

### C9 — Public boundary

Public results expose semantic coordinates, support, curation status/review
coordinates and authorized audit data only. SQLite tables, module/class
internals, filesystem paths and raw diagnostics remain internal.

### C10 — Exact-head proof

Ruff, Black, zero-error typing, full pytest/coverage, plugin notice delivery,
built distribution, installed non-editable MCP, schema transition,
Functional Pyramid production topology, release-note extraction and registry
validation must pass on the exact release candidate without weakening a gate.

## 7. Completion condition

Beta 2 is implementation-complete only when a fresh installed process can prove:

```text
working agent captures supported meaning
→ capture is retained but not shared
→ reviewer discovers CURRENT pending capture
→ reviewer curates exact stable revision
→ future agent reuses CURRENT + CURATED knowledge
→ Span detects evidence/governance change
→ unchanged meaning re-establishes support without losing curation
→ changed meaning becomes CAPTURED and requires re-curation
```

while the Functional Pyramid remains the independent owner of governing
applicability and exactly three public MCP operations remain throughout.
