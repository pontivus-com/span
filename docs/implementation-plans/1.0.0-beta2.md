# Span 1.0.0 Beta 2 implementation plan

**Status:** canonical design complete; implementation open  
**Target package:** `1.0.0b2`  
**Target MCP Registry version:** `1.0.0-beta.2`  
**Target repository schema:** `15`  
**Installation Functional Pyramid schema:** `1` unchanged  
**Public MCP operations:** exactly `ask`, `record`, `reconsider`

This plan implements the Beta-2 product amendment already owned by the canonical
requirements pyramid. It is not an independent source of product requirements.

## 2. Beta-2 product change

Beta 2 separates two semantic moments that Beta 1 treated as one:

1. **capture** — the engineering agent records supported meaning while its
   evidence and reasoning are fresh;
2. **curation** — a separate reviewer act accepts the exact semantic revision
   for shared reuse.

Ordinary Answer eligibility becomes:

```text
support == CURRENT
AND curation == CURATED
```

This is intentionally orthogonal to the Functional Pyramid. Curation never
creates authority, changes applicability, or substitutes for route/authority
support.

The public surface remains exactly three MCP operations. Curation is an
understanding update within `record`, and pending curation is obtained through
`ask`.

## 3. Non-goals

Beta 2 does not:

- add a fourth `curate` MCP operation;
- run a model or background curator inside Span;
- require LangChain, LangSmith or another external framework;
- make curation proof of semantic truth;
- make curation a Functional Pyramid layer;
- infer governing authority;
- add a second semantic content store;
- add similarity-based approval/deduplication;
- weaken support/currentness checks;
- auto-approve Beta-1 knowledge during migration.

## 4. Work packages

### B2-01 — Canonical carriers and grammar

**Authority:** F13; L17; FD-95–FD-99; Technical Design §23.

Add the minimum canonical model vocabulary:

- `CurationState = CAPTURED | CURATED`;
- one immutable curation disposition carrier;
- one understanding curation action input;
- `PendingCurationSelector`;
- one pending-curation result/item projection.

Requirements:

- one canonical carrier per boundary;
- no mutable duplicate approval flag on `SupportedConclusion`;
- no DTO/shadow public/internal shapes;
- generated schema and strict decoder use the same canonical declaration;
- pending items use exact existing semantic coordinates rather than copied
  semantic content where a reference suffices.

**Exit:** canonical model/schema compiles and generated public grammar exposes no
new tool.

### B2-02 — Repository schema 15

**Authority:** Technical Design §§23, 25.

Implement repository schema 15 with one immutable curation persistence owner.

Persist enough information to prove:

- exact `ConclusionRevisionRef`;
- understanding version accepting the curation;
- reviewer reasoning;
- provenance;
- acceptance time;
- explicit versus inherited-confirmation origin.

Current curation state is derived from the exact-revision disposition. Do not
store both a disposition and a mutable curated flag.

**Exit:** schema 15 store round-trips explicit and inherited curation history.

### B2-03 — Explicit 14 → 15 transition

**Authority:** FD-95–FD-102; Technical Design §25.

Extend the existing offline transition path.

Preserve exactly:

- understandings and versions;
- conclusion revisions;
- support dependencies;
- observations/discovery;
- challenges/dispositions;
- verification runs;
- ordinary receipts;
- FunctionalRouteSupport and dependency indexes;
- repository identity/boundaries.

Create zero curation dispositions for pre-existing revisions.

After transition:

- every Beta-1 semantic revision projects CAPTURED;
- current revisions are discoverable through pending curation;
- none is ordinary Answer content before explicit curation;
- installation Functional Pyramid schema/state is unchanged.

Add inspect/apply/verify/rollback coverage and interruption recovery.

**Exit:** a schema-14 fixture transitions without semantic/audit loss and with
empty curation state.

### B2-04 — Understanding writer

**Authority:** L17; FD-96–FD-98, FD-102; Technical Design §24.2.

Extend the existing understanding update owner with `curate`.

Rules:

- target one or more existing current conclusion lineages under
  `expected_version`;
- derive exact revisions server-side;
- require non-empty curation reasoning;
- create no semantic conclusion revision;
- change no statement, assertion nature, semantic scope or support;
- advance the immutable understanding version;
- use existing repository request identity, receipt, replay and CAS behavior;
- reject mixing `curate` with add/confirm/correct/replace/withdraw;
- if review finds a semantic defect, use challenge/correct/replace/withdraw
  before curation.

Semantic transition rules:

- create/add/correct/replace → CAPTURED;
- withdraw → non-reusable;
- confirm of CURATED unchanged meaning → inherited CURATED;
- confirm of CAPTURED unchanged meaning → CAPTURED.

**Exit:** writer/service/store tests prove every transition and concurrency case.

### B2-05 — Answer and status composition

**Authority:** F2, F13; L2, L17; FD-23–FD-25, FD-95, FD-101.

Modify the one canonical Answer composition path.

- Answer includes only CURRENT + CURATED revisions.
- CURRENT + CAPTURED revisions project through pending status/references.
- If no Answer-eligible revision exists but current captures do,
  return `Gap/pending_curation`.
- Existing invalidated/unverifiable/unassessed precedence remains unchanged
  when no current capture exists.
- A mixed surface can return reusable conclusions while also reporting pending
  and stale siblings.

Do not add a second curation-specific answer service.

**Exit:** all Answer/Gap/status tests cover mixed curation/support states.

### B2-06 — Pending-curation obtain

**Authority:** FD-99; Technical Design §24.1.

Implement `ask(PendingCurationSelector{repository_id})`.

The result is:

- repository-local;
- exact current membership only;
- deterministic;
- bounded/truncatable through existing result-budget rules;
- not similarity ranked;
- not priority scored by a model;
- pure/read-only.

It provides exact coordinates sufficient to retrieve the owning understanding
and perform review.

**Exit:** fresh process/restart and paging tests produce the same deterministic
pending set.

### B2-07 — Reconsider and Functional Pyramid isolation

**Authority:** F1, F4, F11–F13; FD-98, FD-100.

Keep the existing effect engine.

- reconsider traverses captured and curated retained revisions alike;
- reconsider changes support state only;
- no change event changes curation state;
- Functional Pyramid route/authority derivation is unchanged;
- curation has no participation/health/route/authority writer.

Prove combinations including:

- CURATED + CURRENT;
- CURATED + REASSESSMENT_REQUIRED;
- CURATED + UNVERIFIABLE;
- CAPTURED + CURRENT;
- CAPTURED + non-current governance.

Only CURRENT + CURATED is Answer-eligible.

**Exit:** existing governance acceptance remains green plus explicit curation
isolation cases.

### B2-08 — Skills and managed agent guidance

**Authority:** A4, A9, A10; F7, F10, F13; Technical Design §26.

Update managed guidance only after the wire exists.

Working-agent guidance:

- ask before semantic investigation;
- capture supported meaning when established;
- do not self-publish task-local meaning merely because the engineering task is
  complete;
- after edits, use reconsider and dispose support effects.

Reviewer/curator guidance:

```text
ask(PendingCurationSelector)
→ retrieve/review exact captured revision
→ investigate broader knowledge/governance as required
→ repair through existing semantic lifecycle if defective
→ record(actions.curate) only for stable meaning
```

A dedicated curation skill is permitted; a new MCP tool is not.

**Exit:** skills/managed assets contain one consistent lifecycle and no Beta-1
"record means immediate shared reuse" instruction.

### B2-10 — Installed end-to-end lane

**Authority:** Technical Design §27.

The non-editable installed MCP lane must demonstrate:

```text
ask cold surface
→ investigate
→ record supported capture
→ ordinary ask cannot publish it
→ pending selector finds it
→ reviewer retrieves/reviews
→ record curate
→ fresh process ask reuses it
→ source/governance change
→ reconsider
→ confirm unchanged meaning and preserve curation
→ fresh reuse
```

Also demonstrate a semantic correction:

```text
curated revision
→ correction/replacement
→ new CAPTURED revision
→ no shared reuse
→ re-curate
→ shared reuse restored
```

**Exit:** installed distribution proves the complete Beta-2 lifecycle outside
the source tree.

## 5. Verification gates

### G-B2-1 — Pyramid derivation

Every implemented behavior maps upward to G2/A10/F2/F3/F5/F7/F13/L17 and
FD-95–FD-102. No new product rule appears only in code or Layer 4.

### G-B2-2 — Three-tool boundary

The advertised MCP operations remain exactly:

```text
ask
record
reconsider
```

### G-B2-3 — No invented curation

Migration, support evaluation, Functional Pyramid resolution and confirmation
may not silently manufacture explicit curation. The sole exception is the
Layer-3-approved inherited-confirmation mechanism from an already CURATED exact
predecessor.

### G-B2-4 — Functional Pyramid isolation

Curation cannot change participation, health, applicability, route identity or
authority support.

### G-B2-5 — History

Historical snapshots must expose that a revision existed as captured before its
later curation acceptance. No retroactive projection is allowed.

### G-B2-6 — Architecture

No duplicate semantic writer, DTO family, answer composer, support evaluator,
curation-specific effect engine or shell semantic coordinator is introduced.

### G-B2-7 — Exact-head release proof

Ruff, Black, zero-error typing, full tests/coverage, plugin notice delivery,
build/install, schema transition, installed MCP, release-note extraction and
registry validation must all pass on the exact release head.

## 6. Completion condition

Beta 2 is complete only when the repository itself proves:

```text
working agent captures
→ captured meaning is retained but not shared
→ reviewer curates exact stable meaning
→ future agent reuses CURRENT + CURATED knowledge
→ Span detects support/governance change
→ unchanged meaning can be re-established without losing curation
→ changed meaning returns to CAPTURED and requires re-curation
```

with the Functional Pyramid remaining the independent owner of governing
applicability and exactly three public MCP operations throughout.
