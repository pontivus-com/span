# Span 1.0.0 Beta implementation plan

**Status:** design-to-implementation plan. Layers 0–3 for Version 1 Beta are
defined in the canonical requirements pyramid. Runtime implementation is
**blocked at T00** until the Version-1 Layer-4 technical design is closed. This
plan does not authorize publication, live-store migration, or release.

**Target release:** Span 1.0 Beta. The package prerelease identifier is fixed by
the Version-1 technical design/release work; this plan does not create a second
version owner.

**Authority:** [goals](../goals.md) G1–G7,
[foundations](../foundations.md) A1–A9/F1–F11,
[lifecycle contract](../lifecycle-contract.md) L1–L12, and
[functional design](../functional-design.md) FD-1–FD-81. The
[requirements pyramid](../requirements-pyramid.md) governs placement. Layer 4
selects mechanisms; this plan orders implementation and verification and may not
invent product behavior.

## 1. Outcome

Deliver the first Span release whose maintained-understanding model covers both:

1. empirical understanding of implementation and its evidence; and
2. declared governing understanding through the Functional Pyramid.

The implementation must preserve the existing three lifecycle operations:
`ask`, `record`, and `reconsider`. Functional Pyramid resolution is
server-owned orientation and support computation within that lifecycle, not a
fourth MCP operation.

Version 1 Beta is complete only when a participating repository can expose its
declared path/scope → functional-context → functional-rule → governing-rule
chain, normative conclusions automatically depend on that complete route, and
changes on either the implementation or governance side propagate through the
same support/reconsideration model.

Canonical governing sources remain canonical. Span stores/reports identities,
owner references, status, applicability, derivation and support; it does not
create a second copy of governing rule text.

## 2. Non-goals and hard boundaries

This release does **not**:

- infer governing contexts or authority from path names, similarity, document
  class, prominence, adjacency or model judgment;
- merge Functional Context with semantic Surface;
- make descriptive conclusions automatically normative;
- generate a semantic conformance verdict from rule text and code;
- add an authority/pyramid MCP tool;
- introduce a central manually maintained copy of canonical rule prose;
- add repository-specific product/domain identifiers to the generic Span core;
- accept unresolved governance as a complete route;
- retain dual old/new public grammar, duplicate support carriers, compatibility
  parsing or parallel writers;
- publish private adopter requirements or acceptance material.

Private first-adopter requirements may constrain acceptance evidence for this
release, but they are not public Span product authority and must remain under
the gitignored `.context/` tree.

## 3. Prerequisite: close Layer 4 before runtime work

### T00 · Version-1 technical design closure

**Authority:** requirements-pyramid §3–§4; G1–G7; F1, F6, F7, F11; L8, L12;
FD-61–FD-81.

Amend [technical design](../technical-design.md) with exactly the mechanisms
needed to realize the accepted Version-1 behavior. Runtime implementation may
not begin until these decisions are explicit and internally consistent.

Layer 4 must settle:

1. **Canonical carriers and ownership.** Exact carriers for functional-context
   identity/declaration, functional-rule declaration, rule owner reference,
   Functional Pyramid view/provenance, unresolved route finding, and route
   support. Reuse existing `AuthorityBinding` rather than introducing a
   competing authority model.
2. **Declaration discovery.** One repository participation/bootstrap mechanism,
   distributed declaration ownership, and the rule that the bootstrap is
   navigation/configuration rather than authority.
3. **Selector grammar.** A deterministic, typed scope-selector grammar for exact
   path, prefix/directory and any other accepted selector forms. It must make
   both membership and broad-scope intersection decidable as required by FD-62.
4. **Repository/workspace resolution.** How registered repositories expose
   stable cross-repository context/rule identities, including the distinction
   between `REPOSITORY_UNAVAILABLE` and an unknown identity in an available
   repository.
5. **Authority-source binding.** How a functional rule points to the existing
   authority-support owner and canonical source identity without copying rule
   prose.
6. **Route identity.** Canonical serialization/fingerprint inputs for FD-73:
   semantic scope, direct/inherited context closure, rule membership, owner,
   layer and governing edges, excluding copied rule prose.
7. **Persistence and migration.** The next store schema, exact mapping from the
   current schema, preservation of existing semantic history/receipts, and
   offline transition/rollback rules. No runtime dual-write or compatibility
   decoder.
8. **Resolver ownership.** Pure-core versus port/service/shell responsibilities
   for declaration validation, graph resolution, cross-repository access and
   source observation.
9. **Public projection.** Exact wire carriers for
   `FunctionalPyramidView | FunctionalPyramidUnavailable | None` in current
   Answer/Gap results without changing the closed result union.
10. **Administrative surface.** The non-MCP validation/inspection capability
    used by installation and CI. It may expose lookup/check functionality to an
    operator but must not become a public agent lifecycle tool.
11. **Bounds.** How large route/provenance views truncate or continue while
    preserving the fact that the route is incomplete and never converting an
    unresolved graph into an apparently resolved one.
12. **Release/migration identity.** Candidate package version, schema identity,
    backup/restore compatibility and rollback boundary.

T00 closes by a requirements audit showing every mechanism maps to an FD/L/F/G
owner and no new product rule exists only in Layer 4.

## 4. Implementation work

### T01 · Add the generic Functional Pyramid domain model

**Authority:** F1, F11; L12; FD-61, FD-65–FD-74.

Implement the canonical typed carriers selected by T00 in
`src/span/core/model/` (or the single existing canonical carrier package
chosen by Layer 4).

Requirements:

- functional contexts and semantic surfaces remain different carrier families;
- context inheritance is zero-to-many;
- context coverage is zero-to-many selectors;
- functional rules carry stable ID, layer, canonical authority reference and
  direct governing IDs;
- P0/P1/P2S/P2W/P3/P4 is one closed layer vocabulary;
- unresolved reasons are the closed FD-71 vocabulary;
- provenance is typed, not an explanatory string;
- no carrier contains canonical rule prose;
- no generic carrier contains adopter-specific names or paths.

Add carrier validation tests for invalid identities, duplicate/unknown fields,
illegal layer values and malformed references.

### T02 · Implement declaration loading, validation and route resolution

**Authority:** G1, G4, G7; F11; FD-61–FD-74, FD-80.

Implement the declaration provider/port and pure resolver chosen by T00.

The resolver must:

- distinguish non-participating repositories from participating repositories
  with invalid/incomplete declarations;
- normalize repository-relative semantic scope;
- find every directly applicable context by deterministic scope intersection;
- include narrower contexts intersecting a broad service/domain/repository scope;
- compose all matches rather than choosing a most-specific winner;
- expand context inheritance to closure;
- collect all referenced rules and walk governing edges to accepted roots;
- preserve per-scope provenance while deduplicating shared contexts/rules;
- follow cross-repository identities only through configured repository
  bindings;
- distinguish unavailable repository from unknown context/rule;
- surface every FD-71 unresolved reason;
- detect context/rule cycles;
- produce deterministic order and route identity.

No source-tree scan for "similar" documents, fuzzy match, model call or fallback
owner selection is permitted.

### T03 · Extend support with Functional Route support

**Authority:** G1, G3; F1, F2, F7, F11; L12; FD-9–FD-16, FD-73, FD-75,
FD-79, FD-81.

Add the fifth support branch without duplicating the existing evaluator.

- Route support is server-derived only.
- Current route support means the complete route resolves and its route identity
  equals the recorded route identity.
- Changed route identity means `REASSESSMENT_REQUIRED`.
- Operationally uncheckable or unresolved route means `UNVERIFIABLE`.
- Applicable authority content/status continues to use the canonical
  `AuthorityBinding` support evaluator rather than being folded into route
  identity.
- Combined state precedence and complete findings remain FD-15/FD-16.

Audit every support union, serializer, store mapping, snapshot/audit projection,
receipt path and premise evaluator for the added support branch. There must be
one support model and one evaluation path.

### T04 · Derive normative governance support during record

**Authority:** A4, F5, F7, F11; L7, L12; FD-30–FD-37, FD-75–FD-77.

After the semantic scope is fixed but before a normative create/update is
accepted:

1. resolve the complete Functional Pyramid route for that scope;
2. reject no caller field merely because the governance is incomplete;
3. make the conclusion non-supportable when the required route is unresolved;
4. derive one route-support dependency;
5. derive authority dependencies for every applicable rule;
6. combine them with caller-supplied empirical/discovery/premise/external
   authority support;
7. persist one canonical dependency set.

The caller has no public field that can suppress, replace or narrow the derived
route/authority set.

Descriptive conclusions follow existing behavior and do not automatically gain
route support. Explicit authority support remains valid when semantically
appropriate.

Exercise create, add, confirm, correct and replace. Preserve withdrawal
semantics, version compare-and-set, request replay and challenge settlement.

### T05 · Compose Functional Pyramid orientation into ask

**Authority:** G1, G4, G7; F6, F10, F11; L1–L3, L8, L12; FD-23–FD-29,
FD-72, FD-74, FD-78.

Extend current Answer/Gap composition with the exact T00 projection:

- non-participating repository → `functional_pyramid=None`;
- participating and evaluable → `FunctionalPyramidView`;
- participating but operationally unevaluable →
  `FunctionalPyramidUnavailable`;
- unresolved governance remains a typed `UNRESOLVED` view, not
  `Unavailable`.

A cold surface can return `Gap/unassessed` plus a resolved route. A current
descriptive Answer may coexist with unresolved governance. A normative
conclusion whose required route support is non-current must not appear as current
answer content.

Do not add a new result union member or a separate operation. Preserve exact
selectors, historical retrieval, continuation, evidence admission and public
failure taxonomy.

### T06 · Propagate governance changes through reconsider

**Authority:** G3; F4, F11; L10, L12; FD-17–FD-22, FD-79, FD-81.

Teach change analysis which repository paths own Functional Pyramid
declarations and canonical authority sources.

For a changed scope:

- retain ordinary containment/source/discovery analysis;
- identify route dependencies whose declaration graph may be affected and
  re-evaluate them;
- identify applicable authority dependencies whose canonical source changed and
  re-evaluate them;
- include affected normative conclusions as direct support effects;
- preserve premise closure as indirect effects;
- do not mark a conclusion stale merely because a declaration file path changed;
  the owning support evaluator decides whether route/authority identity actually
  changed;
- preserve deterministic deduplication and bounded re-establishment context.

Verify governance-only changes that require reassessment while implementation
source remains unchanged.

### T07 · Persist and migrate the Version-1 graph/support state

**Authority:** A1–A3; F2–F4; L4; FD-35–FD-48, FD-73, FD-81 plus T00's Layer-4
migration decision.

Implement the offline transition chosen by T00.

Preserve:

- existing understanding/version/revision history;
- challenge/disposition history;
- observations and discovery support;
- authority bindings;
- receipts and replay semantics where the current retention contract promises
  them;
- verification records and qualification behavior.

Add only the Version-1 persistent state required by the accepted technical
design. Do not fabricate historic Functional Pyramid support for old normative
conclusions. T00 must classify how pre-Version-1 normative conclusions are
qualified after migration; implementation follows that decision exactly.

Exercise interrupted transition, eligibility/refusal, archive/backup,
post-transition integrity, rollback boundary and old-runtime refusal according
to the established store-transition architecture.

### T08 · Add administrative validation and installation integration

**Authority:** F6, F7, F11; L8, L12; FD-61–FD-72, FD-80.

Implement the T00 administrative surface for setup/CI:

- validate repository participation/bootstrap declarations;
- validate declaration syntax and canonical ownership;
- build/refresh any derived index chosen by Layer 4;
- validate cross-repository references against the repositories available to
  the installation;
- report coverage, cycles, duplicate owners, invalid edges and unresolved
  references;
- support deterministic operator inspection of a path/scope for diagnosis.

This is installation/administration, not a fourth MCP lifecycle operation.
Generated indexes/caches are projections and may not become authority.

### T09 · Public schemas, managed guidance and host delivery

**Authority:** A4, A8, A9; F6, F10; L8, L12; FD-49–FD-58.

Update one canonical public grammar and its generated/managed projections.

- `ask`/Answer/Gap expose Version-1 Functional Pyramid state.
- `record` does not require caller Functional Pyramid bookkeeping.
- `reconsider` remains the after-change lifecycle operation.
- Host/agent guidance tells an agent to inspect the returned governing route
  before deriving a normative/conformance judgment.
- Guidance never instructs an agent to infer missing governance or call a
  separate authority tool.
- Existing descriptive workflows remain usable for non-participating
  repositories.

Capture the installed package over direct MCP and each claimed managed host.
Keep host limitations explicit.

### T10 · Generic functional acceptance

**Authority:** functional design §15.

Automate every Version-1 functional acceptance case, including:

- non-participating compatibility;
- cold participating path;
- overlapping contexts;
- disconnected path coverage;
- multi-path and broad semantic scopes;
- paired and missing cross-repository authority;
- all closed unresolved reasons;
- server-derived normative support;
- descriptive support independence;
- authority-content versus route-applicability change;
- implementation change;
- mixed descriptive/current plus unresolved-governance answer;
- canonical-source singularity;
- exactly three MCP tools.

The fixtures must be generic. Product/adopter-specific names, source paths and
rule IDs belong only in private acceptance material, not public unit fixtures
unless intentionally anonymized.

### T11 · Private first-adopter acceptance

**Authority:** G5 plus the private first-adopter requirement document under
gitignored `.context/`.

Execute the Version-1 candidate against the private first-adopter acceptance
matrix only after T01–T10 are green.

This gate demonstrates that the generic design handles a real paired-repository
authority graph with distributed canonical ownership, broad and overlapping
contexts, cross-repository governing edges, standalone-repository limitations,
workflow/backend boundary seams and governance-only invalidation.

The private document and raw evidence remain outside Git and distributions.
Only sanitized generic findings may be promoted into public product docs, and
only when they reveal a generic product requirement rather than adopter data.

A failure here is handled as follows:

- generic Functional Pyramid defect → fix Span at the owning Layer-0–4 boundary;
- adopter declaration defect → fix the adopter declaration, not Span;
- unresolved adopter authority → keep unresolved; Span must not invent the
  missing relationship;
- adopter-only preference → do not add it to the generic product.

### T12 · Version-1 Beta release closure

Before declaring the beta candidate complete:

1. run the full Python suite, Ruff, Black and zero-error typing gate;
2. run installed/non-editable MCP acceptance;
3. run store transition/backup/restore gates required by T00;
4. verify exactly three advertised MCP tools;
5. run the generic Version-1 acceptance set;
6. run the private first-adopter acceptance set and retain its evidence outside
   Git;
7. audit public wire output for internal/store/filesystem leakage;
8. audit the source diff for duplicate carriers, layer inversions, shell
   semantics in core/service, exception-text classification, compatibility
   parsing and repository-specific coupling;
9. map every changed behavior to FD/L/F/G authority;
10. measure the Version-1 task class under G5/F8: obtaining retained empirical
    understanding plus governing applicability must beat reconstructing both
    manually for the same task class.

A beta label does not waive any correctness requirement. It permits explicit
delivery/host limitations; it does not permit unresolved internal contract
contradictions or silently incomplete governance.

## 5. Expected source ownership

T00 may refine exact file placement but must preserve these architectural
boundaries:

| Responsibility | Expected owner |
| --- | --- |
| Functional Pyramid identities, declaration carriers, route/provenance and pure graph rules | `src/span/core/` |
| Cross-repository/declaration/authority capability interfaces | `src/span/ports/` |
| Ask/record/reconsider composition and route-support orchestration | `src/span/service/` |
| Filesystem/config, registered-repository discovery, persistence, index/cache and MCP projection | `src/span/shell/` |
| Public product/contract/technical documentation | `docs/` |
| Private first-adopter requirements and raw acceptance evidence | `.context/` |

The existing canonical `AuthorityBinding`, support evaluator, evidence source,
receipt owner, lifecycle store, surface model and store-transition mechanisms are
the starting mechanisms. Reuse is decided by T00/source inspection; this plan
does not authorize copying or parallel implementations.

## 6. Cross-cutting completion audit

For every T01–T12 work item record:

- governing requirement IDs;
- exact producer/carrier/consumer path changed;
- tests/captures proving the behavior;
- any unresolved decision;
- whether the change is generic or adopter-specific.

Completion is blocked by any of the following:

- a Functional Pyramid behavior that exists only in implementation and has no
  Layer-0–3 owner;
- a Layer-4 mechanism not fixed by the technical design;
- a second authority or route carrier;
- copied canonical rule prose in Span state;
- caller-optional normative governance support;
- most-specific-wins or other obligation-dropping match behavior;
- fuzzy/semantic authority inference;
- cross-repository filesystem assumptions that bypass stable repository/rule
  identity;
- a private adopter requirement appearing in published Span product authority;
- public MCP tool count other than three;
- an unresolved first-adopter failure misreported as generic success.

## 7. Documentation and release reconciliation

When the implementation is verified, reconcile the public surfaces that describe
shipped behavior: README/overview, scope/FAQ, architecture/ports, lifecycle,
freshness/support, authority/trust, interpretation/recording, MCP reference,
install/recovery, managed agent guidance, acceptance and changelog.

Do not update those guides ahead of verified behavior merely because the target
contract exists. The canonical Layer-0–4 documents may describe target
requirements/mechanisms; shipped-product guides must continue to distinguish
target design from observed release behavior until the candidate is verified.

The first-adopter requirement document remains private under `.context/` and is
never linked from published documentation.
