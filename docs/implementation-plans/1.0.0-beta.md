## 1. Outcome

Deliver the first Span release whose maintained-understanding model covers both:

1. empirical understanding of implementation and its evidence; and
2. declared governing understanding through the Functional Pyramid.

The implementation must preserve the existing three lifecycle operations:
`ask`, `record`, and `reconsider`. Functional Pyramid resolution is
server-owned orientation and support computation within that lifecycle, not a
fourth MCP operation.

Version 1 Beta is complete only when an ACTIVE repository can expose its
declared path/scope → functional-context → functional-rule → governing-rule
chain, normative conclusions automatically depend on that complete route, and
changes on either the implementation or governance side propagate through the
same support/reconsideration model.

Canonical governing sources remain canonical. Span stores/reports identities,
owner references, status, applicability, derivation and support; it does not
create a second copy of governing rule text.

## 2. Non-goals and hard boundaries

This release does **not**:

- infer governing contexts or authority from path names, similarity, document
  class, prominence, adjacency or model judgment;
- merge Functional Context with semantic Surface;
- make descriptive conclusions automatically normative;
- generate a semantic conformance verdict from rule text and code;
- add an authority/pyramid MCP tool;
- introduce a central manually maintained copy of canonical rule prose;
- add repository-specific product/domain identifiers to the generic Span core;
- accept unresolved governance as a complete route;
- retain dual old/new public grammar, duplicate support carriers, compatibility
  parsing or parallel writers;
- publish private adopter requirements or acceptance material.

Private first-adopter requirements may constrain acceptance evidence for this
release, but they are not public Span product authority. Detailed adopter
requirements/evidence belong in the adopter repositories' gitignored
`.context/span/functional-pyramid/` trees wherever practicable; Span's own
gitignored `.context/` is limited to minimal generic coordination when
unavoidable.

mechanisms are the starting mechanisms. Reuse/adaptation is fixed by technical
design §§17–22; this plan does not authorize copying or parallel implementations.

## 6. Cross-cutting completion audit

For every T01–T13 work item record:

- governing requirement IDs;
- exact producer/carrier/consumer path changed;
- tests/captures proving the behavior;
- any unresolved decision;
- whether the change is generic or adopter-specific.

Completion is blocked by any of the following:

- a Functional Pyramid behavior that exists only in implementation and has no
  Layer-0–3 owner;
- a Layer-4 mechanism not fixed by the technical design or not assigned to a
  task in §4.1;
- a second authority or route carrier;
- declaration fragments accepted as complete Functional Pyramid declarations;
- a Functional Pyramid replay that mutates/expands its immutable accepted
  dependent-effect refs instead of live-projecting only those refs;
- schema-14 persistence that differs from technical design §19 without an
  explicit Layer-4 amendment;
- copied, summarized or embedded canonical rule prose in Span pyramid state;
- an adoption transition or Functional-Pyramid runtime integration behavior
  that exists in code but not in lifecycle §7;
- treating a successful receipt/acceptance as lifecycle completion when its
  required qualification or returned dependent-effect projection remains
  non-current/actionable;
- dropping an earlier accepted Functional Pyramid write's immutable dependent
  effect obligation during a later DEGRADED repair/revision loop;
- representing conformance as an assertion nature other than NORMATIVE;
- caller-optional normative governance support;
- most-specific-wins or other obligation-dropping match behavior;
- fuzzy/semantic authority inference;
- cross-repository filesystem assumptions that bypass the explicit pyramid
  instance and stable repository/rule identity;
- repository registration silently activating Functional Pyramid participation;
- a public skill, fixture, example or capture leaking private adopter identity,
  topology or governing content;
- a private adopter requirement appearing in published Span product authority;
- public MCP tool count other than three;
- an unresolved first-adopter failure misreported as generic success;
- a current-release README/doc/marketing claim that is not supported by observed
  candidate evidence;
- stale current-version/schema/lifecycle claims surviving in shipped-product
  documentation;
- package, tag, GitHub prerelease, changelog or MCP Registry version metadata
  that does not follow technical design §21's deterministic release identity;
- duplicated release notes or marketing feature lists that contradict the
  canonical changelog.

## 7. Documentation and release reconciliation

T12 owns the complete major-release documentation, changelog, versioning and
marketing/discovery reconciliation. Shipped-product guides are updated from
verified T10/T11 evidence, not merely because target design exists. T13 then
verifies the assembled release before publication.

The canonical Layer-0–4 documents may describe target requirements/mechanisms;
they remain authority and are not converted into launch copy. Public README,
guides, examples, package/registry metadata, changelog and external marketing
surfaces must instead describe the observed candidate and its explicit limits.

Detailed first-adopter requirements/evidence remain private in the adopter
repositories' gitignored `.context/span/functional-pyramid/` trees wherever
practicable and are never linked from published Span documentation.
