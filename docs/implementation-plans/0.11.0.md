This plan governs the implemented source candidate and its remaining verification. It does not authorize running shared workflows, changing production, publishing a release, or modifying live user stores.

### T02 · Separate context and submission identity (#2)

**Authority:** A2, L4, L7, FD-2–FD-4, FD-40, FD-42–FD-45, FD-59. The offline transition mechanism is owned by [technical design §14](../technical-design.md#14-offline-schema-transition).

**Frozen Layer-4 decision.** Technical design §§9.2, 10 and 14 define the single canonical `ContextBinding`, its persisted `binding_digest`, and the exact schema-12 to schema-13 drain/preservation mapping. Implement that decision without a second projection or a legacy-context rebinding path.

`LifecycleService._resolve_record_request` currently passes the whole record wire to `issue_context` and appends `:record-context` to the caller's request ID. Replace the arbitrary digest input and remove that suffix for newly issued record contexts. Key caller-owned recovery by the repository and the caller's actual request identity. Derive one canonical binding from the question when applicable, effective operational scope, and actual source selection, including ranges and complete discovery scopes. Use the same inputs that drive admission. Check every issuance caller, including explicit ask admission and challenge issuance. Preserve fresh Span-owned issuance for changed-scope reconsider.

Keep the complete write digest and retained receipt resolution at the existing submission owner. Resolve a retained receipt before any new-write context or evidence work. Preserve fixed scope, expiry, liveness and atomic acceptance.

**Schema-12 to schema-13 cutover.** The stored digest changes meaning, so schema 13 owns the new binding semantics. The legacy digest commits to the original wire payload, and continuations check it. Stored scope and admitted membership alone cannot establish every original evidence selection. Keep schema 12 and its runtime authoritative during the drain. Use the existing offline transition, archive, verification and activation owners.

- Arrange an authorized drain in which legacy work can recover while ordinary new context issuance winds down. Before staging and again before activation, verify eligibility under the existing exclusive store ownership boundary. Refuse the cutover while any legacy context is live under the current liveness rule, including a live context with no expiry. Keep the old store usable after refusal. Waiting a fixed number of days is insufficient evidence of eligibility.
- Once eligible, stage schema 13 without the legacy operational contexts or their source and discovery memberships. Preserve the original retained receipts, including keys, digests and expiry, as well as durable semantic history and the observations it relies on. Verify references from receipts and history independently, including history whose receipt has expired. The canonical schema gate rejects a schema-12 store under the new runtime. Every newly issued context uses the new binding projection.
- Verify the transition with disposable pre-change stores. Cover a refused cutover followed by successful schema-12 continuation recovery, attempted old-writer activity across the ownership boundary, an eligible activation, and exact post-cutover retrieval of retained receipts and their history. Exercise interruption and restart through the existing transition owner. Verify rollback before new writes are accepted. Once schema 13 accepts writes, recovery must account for those writes and their receipts before serving the previous store.

Verify these outcomes:

- Structural rejection occurs before admission and issues no context.
- A rejected semantic write corrected without changing its binding recovers the same context.
- A changed binding under the same request identity receives `CONTEXT_BINDING_CONFLICT`.
- An identical accepted submission replays, including across restart within the retention window.
- Different content under an already accepted identity receives `REPLAY_CONFLICT`.
- A rejected write commits no version, revision or challenge disposition and consumes no context.

### T04 · Fix update validation and lookup failure classification (#7)

Resolve any early stale outcome under the same receipt-first ordering as acceptance, so a concurrent accepted write under the same request identity still determines replay or replay conflict. Include repository setup and routing, exact lookups, persisted data and immutable observation checks, context and command identity invariants, replay and challenge conflicts. Carry absence distinctly from operational failure at the store boundary. Apply the classification at the owner that knows what each failure means:
