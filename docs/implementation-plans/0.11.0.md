# Span 0.11.0 implementation plan

**Status:** Proposed. Release verification deferred.

**Implementation choices:** T02 uses an offline schema-12 to schema-13 cutover after legacy contexts drain. T07 uses one context-free recording to re-establish the conclusion and resolve the challenge when new evidence supports that conclusion. The release still requires cutover authorization, transition verification, and an end-to-end MCP test of the reported challenge scenario.

**Basis:** The original agent's Span usage report from the 18–19 November 2026 CDG governance remediation session and the subsequent review of the proposed remedies. The report establishes what happened in that session. Source inspection and reproduction establish where each defect is produced and whether a candidate fixes it.

## 1. Outcome and authority

Fix the ten reported failures and sources of friction at their owning boundaries. Preserve the useful before-read experience, precise change impact, explicit challenge resolution, audit retrieval, and visible distinction between current and stale understanding.

Apply [Span's operating rules](../../AGENTS.md) and the [requirements pyramid](../requirements-pyramid.md). Trace each change to its owner in [goals](../goals.md), [foundations](../foundations.md), the [lifecycle contract](../lifecycle-contract.md), and the [functional design](../functional-design.md). Use the [technical design](../technical-design.md) for implementation choices. Goals G1–G6, the existing lifecycle contract and functional behavior govern this release. An unresolved contract gap requires an explicit decision at the layer that owns it before a mechanism is selected.

The public operations remain `ask`, `record`, and `reconsider` (L8). Keep one typed declaration per boundary and one owner per decision. Fix the producer of the invalid state. For every defect, trace the producer, its carrier, and downstream consumers, and look for the same failure pattern elsewhere in production code. Exclude compatibility aliases, duplicate carriers or writers, exception-text parsing, automatic identity changes on retry, ad hoc changes to retained state, and freshness exemptions.

This plan defines future implementation and verification. It does not authorize running shared workflows, changing production, publishing a release, or modifying live user stores.

## 3. Implementation work

### T01 · Copyable surface recovery and repository ingress (#1)

**Authority:** A8, A9, F7, F10, lifecycle §4.1, FD-26, FD-41.

Define the existing public `SurfaceReference` with exactly `kind` and `locator`. Remove its nested `repository_id` and the ask and recorded-question presence rules for that retired field. In `AnswerService._resolve`, emit this public carrier for each ambiguity candidate. Keep `SurfaceKey` as the internal resolved identity. The shared schema and strict decoder reject any supplied nested `repository_id`, including explicit null, as an unknown field. T03 supplies the actionable rejection. Ordinary obtain uses the original top-level repository, and exact selectors retain their own repository binding.

Verify that an unchanged candidate works as `surface`, that nested repository values including explicit null are rejected where the lifecycle contract forbids them, and that both original placement errors identify the corrective field and include a valid example. Verify the advertised schema and runtime agree.

### T02 · Separate context and submission identity (#2)

**Authority:** A2, L4, L7, FD-2–FD-4, FD-40, FD-42–FD-45, FD-59. The offline transition mechanism is owned by [technical design §14](../technical-design.md#14-offline-schema-transition).

`LifecycleService._resolve_record_request` currently passes the whole record wire to `issue_context` and appends `:record-context` to the caller's request ID. Replace the arbitrary digest input and remove that suffix for newly issued record contexts. Key caller-owned recovery by the repository and the caller's actual request identity. Derive one canonical binding from the question when applicable, effective operational scope, and actual source selection, including ranges and complete discovery scopes. Use the same inputs that drive admission. Check every issuance caller, including explicit ask admission and challenge issuance. Preserve fresh Span-owned issuance for changed-scope reconsider.

Keep the complete write digest and retained receipt resolution at the existing submission owner. Resolve a retained receipt before any new-write context or evidence work. Preserve fixed scope, expiry, liveness and atomic acceptance.

**Schema-12 to schema-13 cutover.** The stored digest changes meaning, so schema 13 owns the new binding semantics. The legacy digest commits to the original wire payload, and continuations check it. Stored scope and admitted membership alone cannot establish every original evidence selection. Keep schema 12 and its runtime authoritative during the drain. Use the existing offline transition, archive, verification and activation owners.

- Arrange an authorized drain in which legacy work can recover while ordinary new context issuance winds down. Before staging and again before activation, verify eligibility under the existing exclusive store ownership boundary. Refuse the cutover while any legacy context is live under the current liveness rule, including a live context with no expiry. Keep the old store usable after refusal. Waiting a fixed number of days is insufficient evidence of eligibility.
- Once eligible, stage schema 13 without the legacy operational contexts or their source and discovery memberships. Preserve the original retained receipts, including keys, digests and expiry, as well as durable semantic history and the observations it relies on. Verify references from receipts and history independently, including history whose receipt has expired. The canonical schema gate rejects a schema-12 store under the new runtime. Every newly issued context uses the new binding projection.
- Verify the transition with disposable pre-change stores. Cover a refused cutover followed by successful schema-12 continuation recovery, attempted old-writer activity across the ownership boundary, an eligible activation, and exact post-cutover retrieval of retained receipts and their history. Exercise interruption and restart through the existing transition owner. Verify rollback before new writes are accepted. Once schema 13 accepts writes, recovery must account for those writes and their receipts before serving the previous store.

Verify these outcomes:

- Structural rejection occurs before admission and issues no context.
- A rejected semantic write corrected without changing its binding recovers the same context.
- A changed binding under the same request identity receives `CONTEXT_BINDING_CONFLICT`.
- An identical accepted submission replays, including across restart within the retention window.
- Different content under an already accepted identity receives `REPLAY_CONFLICT`.
- A rejected write commits no version, revision or challenge disposition and consumes no context.

### T04 · Fix update validation and lookup failure classification (#7)

**Authority:** A2, A3, A8, L4, lifecycle §§4.1–4.3, FD-19, FD-27, FD-38–FD-41, FD-46–FD-48.

The context-free update path currently looks up the requested version while deriving scope, before the write's compare-and-set check. The SQLite version lookup raises its operational store error on absence. This is a verified path in the current source. Use the baseline to determine whether it caused the specific session failure.

At the update owner, establish the target and expected-version outcome before deriving scope and revisions from that version. Reuse the validated version in command construction and keep the transactional compare-and-set authoritative for races. A preliminary receipt miss cannot authorize a final version rejection. Resolve any early stale outcome under the same receipt-first ordering as acceptance, so a concurrent accepted write under the same request identity still determines replay or replay conflict. Reuse the existing receipt and transition owners. Test both an existing old version and a supplied version that does not exist for a known understanding. A stale expected version must receive the structured current version and a valid recovery when there is no prior acceptance for that request identity.

Classify every production producer of `LifecycleStoreError` and trace consumers that catch its base type. Include repository setup and routing, exact lookups, persisted data and immutable observation checks, context and command identity invariants, replay and challenge conflicts. Carry absence distinctly from operational failure at the store boundary. Apply the classification at the owner that knows what each failure means:

- An unknown caller-supplied exact identity is an actionable `Rejected`. Preserve declared gap behavior for a question with no matching membership.
- A missing or unreadable support dependency has its contract-defined support state. Missing history referenced by an accepted receipt remains explicitly unavailable history.
- Store, provider and schema incompatibility failures that prevent evaluation are `Unavailable` with recovery. Post-commit qualification failure preserves acceptance and its receipt.
- Unexpected defects retain internal diagnostics and use stable tool failure containment. Audit broad exception handlers along these paths.
- Repository setup and registration failures follow the setup boundary. For lifecycle calls, a repository access failure follows the established operational recovery for that call.

Close the finding with the original failing update or an evidence-backed reconstruction, plus successful updates to an older understanding with the correct current version, unknown references, a real operational failure simulation and unaffected sibling creates. Exercise a concurrent commit between the preliminary receipt lookup and the version check. Verify identical same-identity writes replay, different-content same-identity writes conflict, and distinct identities racing on one version yield one acceptance and one version conflict. If the original cause stays unresolved, report the independently fixed paths and leave #7 open.

### T06 · Carry create scope alongside explicit support (#10)

### T07 · Issue a context that supports actual re-establishment (#5)

**Authority:** F4, F7, F9, L10, lifecycle §§4.2–4.3, FD-17–FD-22, FD-59.

`ReconsiderService._reconsider_context` currently receives surface keys and builds a path scope from changed paths and surface boundaries. Derive the bounded context from the affected scope and the actionable conclusions' complete existing evidence requirements. Reuse the existing typed scope union, exact source and discovery observations, and authority and premise owners. Preserve complete scopes and exact refs. Containment-only results produce no additional re-establishment obligations. Preserve affected-set completeness, the returned order and fresh issuance on each changed-scope read.

For the reported case where a newly gathered ADR supports the resulting conclusion and lies outside the original context, use one context-free `record` with the repository binding and current expected version. Put the complete direct support, including the ADR, on the conclusion's `correct` or `confirm` action. In the same request, supply the `resolved` disposition for the same challenge, its expected revision, and the resulting understanding and version. The disposition can omit `evidence_refs` because the action supplies the evidence for the resulting conclusion. Span derives the operational context, admits the direct support, and commits the revision and challenge settlement atomically under the existing grammar.

Verify that journey through MCP using evidence outside the original context. Assert that the same challenge reaches `RESOLVED`, the resolution history names the exact resulting version, and the resulting conclusion is `CURRENT` with the ADR in its recorded support and its original semantic scope intact. Verify that a rejected disposition commits neither effect. Separately, verify that already-declared evidence is within the returned reconsider context and that re-establishment can use it there.

Evidence that supports only the disposition's reasoning still needs a valid disposition-evidence path. Keep `evidence_refs` bound to the context that admitted them. If the baseline shows that the reported ADR served only that role, keep #5 open until the disposition-evidence path is demonstrated. A gap in the existing contract requires a separate Layer 2 decision.

## 6. Cross-cutting compliance gate

Before marking 0.11.0 implementation-complete, require the finding-specific acceptance results and all three audits below for the same release candidate.

1. **Public boundary.** Enumerate and exercise every declared request branch, result variant, rejection, unavailability response and transport error through the packaged MCP. Review the advertised schemas, examples and descriptions alongside the observed payloads. Maintain an explicit allowlist grounded in [lifecycle contract §4.3's public agent boundary](../lifecycle-contract.md#43-reconsider--re-align) for public coordinates, repository-relative evidence locators, opaque handles and authorized audit metadata. Check for runtime class and module names, raw diagnostics and tracebacks, host filesystem or store paths, storage and schema internals, internal issuance keys or digests, context origins, and administrative state. Treat those disclosures as failures. Public wire vocabulary and handles must be usable as declared without interpreting internal state.
2. **Architecture.** Inspect the complete 0.11.0 diff against [Span's operating rules](../../AGENTS.md). Check for layer inversions, `Any` in semantic layers, duplicate DTOs or carriers, multiple writers, compatibility parsing, fallback behavior, exception-text classification, shell semantics in core or service, duplicate evidence or context algorithms, and target-repository coupling. Trace changed behavior from producer through the canonical carrier to its consumers. Existing invariant and isolation gates must pass without weakening their coverage.
3. **Requirements pyramid.** Map each changed behavior from the technical mechanism to the applicable FD, L, F, A and G authority through the [requirements pyramid](../requirements-pyramid.md). Check that each requirement lives at its owning layer, lower layers derive their decisions from higher layers, higher layers stay free of implementation mechanisms, and requirements are stated once. A behavior that cannot be derived from governing authority, or an unresolved conflict between layers, blocks completion.

Record the candidate build and schema identity, each audited branch or code boundary, the applicable requirement IDs, the evidence checked, and any open finding. Report sanitized results and keep raw captures outside Git and distributions. An unresolved compliance finding blocks implementation completion. Cutover and publication remain separately authorized release steps.
