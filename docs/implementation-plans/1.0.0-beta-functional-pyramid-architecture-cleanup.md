# Span 1.0 Beta Functional Pyramid architecture cleanup

**Status:** COMPLETE (2026-11-22) — C00–C08 closed from current
solution-design, implementation and exact-head GitHub Actions evidence.

**Parent campaign:** `docs/implementation-plans/1.0.0-beta.md`.

**Tracking:** GitHub issue #39.

This plan is intentionally separate from T00–T13. Historical task completion
and historical CI receipts do not close cleanup work. The cleanup is complete
only from current evidence against the corrected Layer-4 design and the
production-topology acceptance defined in Technical Design Part C.

## 1. Root cause

Layers 0–3 remain the governing product/functional authority. The audit found no
contradiction requiring their amendment. The failure was Layer-4
construction-detail incompleteness at four integration seams:

1. installation runtime composition was not explicitly separated from composed
   repository `ServiceContext`;
2. Functional Pyramid runtime dependencies were allowed to become optional
   callbacks with semantic fallbacks;
3. support evaluation did not have an explicit repository-qualified
   authority/evidence capability;
4. the service-owned shared effect engine was not specified as genuinely
   multi-repository over physically separate repository stores.

That underspecification enabled shell-owned semantic coordination, repository-
local support assumptions and production paths that silently omitted Functional
Pyramid behavior while manually wired unit tests remained green.

Technical Design Part C was amended on 2026-11-22 before this cleanup's
production work. That amendment is the binding mechanism baseline for C01–C08.

## 2. Cleanup rule: remove wrong architecture

When existing Version-1 code embodies the wrong owner, parallel semantic path,
silent fallback or fake composition boundary, delete it. Do not preserve it
through a shim, wrapper, compatibility bridge or adapter.

Refactor only code whose semantic owner/abstraction is already correct.

Preserve FCIS, separation of concerns, DRY and strict typing:

- `core` is deterministic and effect-free;
- `service` owns semantic operation composition;
- `shell` owns effects, persistence adapters and MCP transport;
- one canonical carrier per boundary;
- no DTO family or second grammar;
- no second support evaluator;
- no second dependency-effect engine;
- no copied authority state;
- no weakened test/gate.

this ownership boundary against the C01 design basis above.

**Disposition: DELETE, not refactor.**

Delete `FunctionalPyramidEffectCoordinator` as a semantic architecture from
`src/span/shell/functional_pyramid.py`.

Delete the shell-owned semantic responsibilities currently implemented there:

- changed-route-identity derivation;

### C02 — establish canonical installation composition

**Status: IMPLEMENTED, SOLUTION-DESIGN VERIFIED, AND BEHAVIOR VERIFIED
(2026-11-22).** MCP, ordinary repository contexts and semantic hooks use the
installation composition root; raw runtime opening remains limited to
installer/readiness work. Verification is against the C02 design basis above.

**Disposition: REFACTOR.**

Refactor the shell composition so raw registered repository capabilities can be
opened independently of `ServiceContext`. Compose one installation runtime
containing the repository-runtime resolver, installation Functional Pyramid
state/declaration/authority/evidence capabilities and one
`FunctionalPyramidService`. Compose ordinary repository services only after
that installation layer exists.

Production Answer/Lifecycle/Support/Reconsider/effect services receive mandatory
Functional Pyramid capabilities. Missing composition is not a domain state.

The implementation must also migrate every semantic consumer, including host
hooks, onto the same installation composition root. Raw runtime opening remains
legal for installer/readiness work only. No semantic caller may invoke
`open_repository_context` without the installation capabilities or recreate a
partial service graph.

**Acceptance:** one installed process cannot return ACTIVE through a Functional
Pyramid status selector while ordinary ask for the same repository projects
UNCONFIGURED; host hooks that evaluate support/dependents use
`InstallationRuntime`; no semantic runtime path can construct a partial
`ServiceContext`.

### C03 — make SupportService repository-qualified

**Status: IMPLEMENTED, SOLUTION-DESIGN VERIFIED, AND BEHAVIOR VERIFIED
(2026-11-22).** External authority/evidence uses the referenced repository
runtime and missing repository-qualified composition fails closed rather than
using the semantic owner's local store. Verification is against the C03 design
basis above.

**Disposition: REFACTOR existing canonical evaluator.**

Retain `SupportService` and FD-15/FD-16 combined-state semantics. Replace
repository-local authority/evidence assumptions with repository-qualified
capabilities.

Required proof: a conclusion in repository A governed by canonical authority in
repository B can evaluate CURRENT, and changing B's authority content causes the
same A dependency to re-evaluate without copying B state into A.

The repository-runtime resolver is mandatory whenever authority/evidence may be
repository-qualified. The evaluator must not fall back to its local
`authority`/`evidence` objects for an external authority merely because the
resolver was omitted. Omitted required composition is an invariant error, not a
support-state decision.

### C04 — make the shared dependency-effect engine multi-repository

**Status: IMPLEMENTED, SOLUTION-DESIGN VERIFIED, AND BEHAVIOR VERIFIED
(2026-11-22).** The effect engine has one repository-qualified construction
shape, ReconsiderService receives that engine, and ordinary changed-scope
traversal invokes Functional Pyramid route impacts unconditionally. Verification
is against the C04 design basis above.

**Disposition: SUBSTANTIAL REFACTOR.**

Retain the existing service-owned dependency/effect algorithm. Delete its
single-store/single-support construction mode and use repository-qualified
access exclusively. A one-repository test supplies a one-entry runtime registry
and support resolver; there is no alternate local architecture.

The one engine owns both ordinary changed-scope and Functional Pyramid delta
roots, direct dependency selection, support re-evaluation, premise closure,
canonical affected projection and one actionable context per repository.

No shell loop over per-repository semantic effect engines may remain.

`ReconsiderService` must receive the already-composed effect engine and may not
construct a local fallback engine. Ordinary `repository_change` must invoke the
Functional Pyramid route-impact resolver unconditionally; UNCONFIGURED/EXCLUDED
participation may legitimately produce an empty impact set, but an absent
resolver may not be interpreted as one.
